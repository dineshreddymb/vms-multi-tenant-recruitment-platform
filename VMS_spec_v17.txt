3.1 Recruiter Signup, Approval and Login — Mandatory Flow
RECRUITER SIGNUP FIELDS — V1: Full Name, Email Address, Mobile Number, Password and Confirm Password. Company/Vendor fields are not part of Recruiter signup. Email is the canonical Recruiter login identity.
Recruiter signup is a public request-creation action only. It does not authenticate the requester and does not create an ACTIVE login account.
The password is hashed with Argon2id (or an approved equivalent) before it is persisted in recruiter_signup_requests. The approving Admin never receives the password or hash.
On APPROVE, the hashed password is transferred into the canonical internal_users account in the same transaction; the pending request is marked APPROVED and linked to created_user_id. On REJECT, no ACTIVE login account is created.
Recruiter login is allowed only when internal_users.status=ACTIVE and role=RECRUITER. The server resolves access_level=STANDARD or ADMIN from authoritative database state.
A rejected Recruiter may submit a new signup request. Each resubmission receives a new request ID; prior REJECTED requests remain historical and audited.
A Recruiter must sign up before login. The signup screen collects the approved Recruiter identity fields and password/confirmation.
Backend validates the request and creates recruiter_signup_requests with status=PENDING. Password material is never stored in plaintext.
No canonical ACTIVE internal_users login identity exists until an ADMIN approves the request.
The request appears in Approval Requests. Only ADMIN Recruiters can approve or reject Recruiter signup requests.
APPROVE creates/activates the canonical Recruiter account as STANDARD by default. REJECT leaves a historical REJECTED request and the requester cannot authenticate.
After approval, the Recruiter logs in using the same signup email and password. Login creates a revocable server-side session and JWT access token.
A rejected Recruiter may submit a new signup request; the old rejected request remains historical and audited.
Frontend visibility is not authorization. Every protected Recruiter endpoint resolves current access_level server-side.
3.2 Two-Admin Authorization Model
The initial initialized Recruiter is ADMIN #1.
Additional approved Recruiters are STANDARD by default.
An existing ADMIN may promote any ACTIVE STANDARD Recruiter to ADMIN when the current active Admin count is below two.
There may be no more than TWO ACTIVE ADMIN Recruiters in the entire application.
Once ADMIN #2 exists, ADMIN #1 and ADMIN #2 have equal Admin authority.
Either Admin may remove the other Admin's Admin privilege. Removal changes ADMIN → STANDARD; it does not delete or disable the Recruiter account.
A Standard Recruiter cannot approve/reject Recruiter signup requests, grant Admin access or remove Admin access.
Admin grant/removal must be transaction-safe, concurrency-safe and audited.

5. Authentication and Session Flow
SESSION MODEL — The user's device remains signed in through a server-side revocable session until the user logs out, the session is revoked, the account is disabled, or the security policy expires the session. Multiple devices create independent sessions.
JWT access tokens should be short-lived and paired with a secure refresh/session mechanism. Do not create an effectively permanent JWT. Logout revokes the session/refresh state so a future refresh cannot issue another access token.
Removing ADMIN access must invalidate Admin authorization on subsequent API checks even if the Recruiter's existing access token has not naturally expired. Authorization is always resolved from current server-side access_level.

Authentication answers WHO the user is; authorization answers WHAT the user may access.
Invalid login response is exactly: 'Invalid email or password. Please check your credentials and try again.'

Multiple devices are supported through independent session identities.

6. Vendor Signup, Approval and Rejection
VENDOR COMPANY IDENTITY / UNIQUENESS — Company Name entered at signup identifies the Vendor/company. Vendor/company names must be normalized for uniqueness comparison (trim whitespace, normalize case and apply the chosen canonical normalization rule) and protected by a database uniqueness constraint/index on the normalized value.
If the normalized company already exists, a new Vendor User signup may proceed through PENDING approval, subject to duplicate-pending-request and login-identity uniqueness protection. Multiple ACTIVE Vendor Users may belong to the same Vendor.
If the normalized company exists, the pending signup is associated with that existing Vendor. If the company does not yet exist, the pending signup request carries the normalized company identity; the Vendor record and Vendor User are created/linked transactionally on approval.
A rejected request does not create an ACTIVE Vendor account.
A second PENDING request for the same Vendor/login identity must not create uncontrolled duplicate accounts. The backend must enforce this with a transaction-safe uniqueness/idempotency rule.
Candidate Vendor Name is never typed manually by the Vendor User. It is derived from the authenticated vendor_id and displayed as the Vendor/company name.
The in-application Approval Requests screen is the authoritative approval mechanism for Vendor signup and Recruiter signup. Email notification is optional/informational and never the source of truth. Recruiter signup approval is ADMIN-only.

21. Submission Idempotency and Retry Safety
POST /api/v1/submissions requires Idempotency-Key for each logical submission attempt.
Idempotency record is bound to authenticated Vendor User and payload/request fingerprint.
Same key + equivalent request returns the original successful result.
Same key + materially different payload returns idempotency conflict.
Same key cannot replay another user's result.
Idempotency persistence and candidate/submission transaction must be coordinated.
Timeout/retry and concurrent same-key behavior must be integration/E2E tested.
22. Database Model and Integrity
INTERNAL USER EMAIL — internal_users.email must be unique after canonical normalization. Recruiter signup must not create two authoritative Recruiter identities for the same normalized email.
RECRUITER REQUEST UNIQUENESS — A normalized Recruiter email may have at most one actionable PENDING signup request at a time. Historical REJECTED requests remain allowed.
VENDOR NAME UNIQUENESS — vendors.normalized_name must be unique. Store the display company name separately if needed, but use normalized_name for equality/uniqueness checks.
VENDOR USER MULTI-ACTIVE SUPPORT — vendor_users must allow multiple ACTIVE rows for the same vendor_id. Do not enforce any database constraint or partial unique index that limits ACTIVE Vendor Users to one per Vendor.

The canonical internal_users record is created/activated only after ADMIN approval.
The first seeded Recruiter is ACTIVE + RECRUITER + ADMIN.

25. Security Architecture
NO LLM/AI API KEYS — V1 must not require OpenAI, Anthropic, Gemini, Grok or any other LLM/AI API key. Deterministic Resume parsing is local/service-controlled and does not call an LLM.
V1 operational secrets are limited to infrastructure/application secrets actually required by the selected stack, such as DATABASE_URL, object-storage credentials, JWT signing/verification secret or key pair, encryption/KMS configuration and any queue credentials. Do not add an AI provider key.
